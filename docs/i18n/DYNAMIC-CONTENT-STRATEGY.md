# FreshCheck — translating DB / AI-generated content (recipes, scans, storage tips)

> Goal: serve recipes & AI content in the user's language **without ever
> re-generating the (expensive) images**, while still accumulating one shared,
> cross-user base of recipes. Decided 2026-06-17.

## The two buckets of dynamic content

| Bucket | Examples | Reused across users? | Strategy |
|---|---|---|---|
| **A. Accumulated / cached** | AI recipes (`recipes_cache`), their hero images | YES — keyed by ingredient signature / slug | English canonical + **lazy translate-and-cache**, image reused as-is |
| **B. Ephemeral / per-scan** | scan freshness verdict, per-item storage advice | NO — unique to one photo/session | **generate directly in the user's locale** (pass locale into the prompt) |

The split matters: bucket A must stay language-pivotable (one English master →
N translations sharing one image) so the cross-user cache + image reuse keep
working. Bucket B is one-shot, so just produce it in the right language the
first time — no translation table needed.

## Bucket A — recipes (the important one)

### How it works today (verified in `generate-recipes/index.ts` + `useRecipes.ts`)
- gpt-5.5 generates a 3-recipe batch **in English**.
- Cached in `recipes_cache` keyed by `signature` = hash of the sorted, normalized
  ingredient-set. Same fridge → same batch, reused across **all** users for $0.
- Each recipe gets `id = slug(name)` (English slug).
- Hero images are generated by a **separate** `recipe-image` function and cached
  in the `recipe-images` Storage bucket **keyed by `slug` (= recipe id)**. The
  client fetches the image by `r.id`.

### The one rule that makes images free forever
**Translations must NOT change `recipe.id` (the slug).** Translate only the
*display* fields; keep `id` = the English slug. Then `recipe-image` resolves the
same cached photo regardless of language. Image generation cost for locales = $0.

Display fields to translate (per recipe):
`name`, `blurb`, `ingredients[].name`, `ingredients[].amount` (units!), `steps[].text`.
Leave untouched: `id`, `minutes`, `difficulty`, `uses_categories` (enum), `icon`
(enum), `from_fridge` (bool), `hero_image_prompt` (unused after image exists).

### Schema — sibling per-locale cache
```sql
create table if not exists recipes_cache_i18n (
  signature text not null,           -- same key as recipes_cache
  locale    text not null,           -- 'fr', 'de', 'ja', ...
  recipes   jsonb not null,          -- translated batch, ids preserved
  created_at timestamptz not null default now(),
  primary key (signature, locale)
);
alter table recipes_cache_i18n enable row level security;  -- service_role only
```
English stays the canonical row in `recipes_cache` (locale 'en' = passthrough, no
i18n row needed).

### Flow (in `generate-recipes`, add a `locale` body param)
1. Produce the English batch as today (cache hit or fresh gpt-5.5 call).
2. If `locale === 'en'` → return English batch (unchanged).
3. Else look up `recipes_cache_i18n(signature, locale)`:
   - **hit** → return translated batch (free, instant). Image slugs unchanged.
   - **miss** → call a cheap translation model on the batch's display fields
     (one JSON-in/JSON-out call, ids preserved) → upsert into
     `recipes_cache_i18n` → return.
4. `recipe-image` is untouched — client still fetches by `r.id`.

Cost per locale = **one cheap text-translation call per ingredient-signature, once
ever**, then $0 + instant for every future user in that language. Images: $0.

### Translation model
Don't use gpt-5.5 (overkill/expensive) for translation. Use the cheapest GA model
that handles culinary terms well (verify latest GA name via vendor docs per the
`feedback_latest_models` rule — candidates: a `gpt-*-mini` tier, or DeepL API).
Translate the whole batch in ONE structured call; instruct: preserve JSON shape,
preserve `id`, translate cooking terms idiomatically, localize units sensibly
(e.g. keep grams; don't convert cups→ml unless natural), keep `amount` concise.

### Favorites / saved recipes (client)
A favorited recipe is stored client-side in the locale the user saw. That's fine —
it already carries translated text + the same `id` (so its image still resolves).
No migration of favorites needed.

## Bucket B — scans & per-item advice
- `scan-image` / `scanAnalysis`: pass the user's `locale`; instruct the model to
  return the verdict, reason, and any advice **in that language**. One scan = one
  call; no caching/translation table. (CJK/Arabic text renders via system-font
  fallback — see fonts note in the i18n plan.)
- Storage-guide / fresh-tips cards: if **static** → they live in the static i18n
  JSON (Part of the UI i18n plan). If **AI-generated per scanned item** → same as
  scans: generate in-locale. (Confirm which in the codebase map.)

## Why not the alternatives
- **Translate eagerly to all 14 locales at generation time** → pays 14× per batch
  for locales nobody may use; wasteful early. Lazy = pay per locale actually used.
- **Generate each batch directly in the user's locale** → breaks the cross-user
  cache (a French batch can't serve a German user) and the "accumulate one base"
  goal. Rejected.
- **Store translations nested inside `recipes_cache.recipes`** → bloats the hot
  English row, complicates the existing cache read path. Sibling table is cleaner.
